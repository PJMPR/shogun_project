# Build the Shogun Schedule service

Implement a dedicated .NET 10 service under `backend/Shogun.Schedule` using Api/Application/Domain/Infrastructure projects. Use EF Core with Npgsql and PostgreSQL. Follow the authentication, JSON, exception handling, health-check, logging, Dockerfile, and project-reference patterns in `backend/Shogun.Assignments`, but use EF migrations rather than `EnsureCreated`.

Read `frontend/pj-studies-schedule/SKILL.md` before changing frontend behavior. Restrict deployment work to `deployment-local` until explicitly asked to support another environment.

## Model the aggregate

Treat `Schedule` as the aggregate root for one reusable weekly timetable. Do not model calendar dates, individual occurrences, odd/even weeks, exceptions, or cancellations yet.

Identify a schedule uniquely by:

- faculty
- academic year
- semester number
- study mode

Use a database unique constraint across those fields. Semester number is required and constrained to 1-8. Derive winter/summer from parity; do not persist a second semester-type truth. Constrain academic year to a canonical value such as `2026/2027`. Use `StudyMode` values `Stationary` and `PartTime`.

Include `Name`, `Status` (`Draft`, `Published`), audit fields, and a concurrency token. The first supported faculty is Wydział Informatyki, but normalize faculty into a `Faculty` entity with stable code, display name, and uniqueness on code so another faculty can be added without changing the schedule schema.

Use UUID primary keys generated by the application or PostgreSQL. Store timestamps as UTC `timestamptz`.

## Use these entities

### Faculty

Persist `Id`, `Code`, `Name`, `CreatedAt`. Seed a stable Informatics faculty code. Do not hard-code the faculty name into schedules.

### Schedule

Persist `Id`, `FacultyId`, `AcademicYear`, `SemesterNumber`, `StudyMode`, `Name`, `Status`, `ConcurrencyToken`, `CreatedAt`, `CreatedBy`, `UpdatedAt`, `UpdatedBy`.

### StudentGroup

Persist `Id`, `ScheduleId`, `Code`, `Name`, `SortOrder`, audit fields, and concurrency token. A group such as G1 is the same group on every weekday. Enforce unique normalized group code and unique sort order within a schedule.

Do not persist the frontend's day-specific `groupsPerDay` representation. Return one ordered group collection and adapt the weekly grid to use it across days.

### ScheduleEntry

Persist:

- `Id`, `ScheduleId`
- nullable external subject identity (`SubjectSource`, `SubjectExternalId`)
- subject snapshots (`SubjectCode`, `SubjectName`)
- `ClassType` (`Lecture`, `Exercises`, `Laboratory`, `Project`, `Seminar`, `Other`)
- normalized `LecturerEmail` as the stable lecturer identifier
- `LecturerDisplayName` as a snapshot for presentation
- nullable free-text `Room`
- `DayOfWeek` constrained to 0-6 using the frontend convention `0=Monday`
- `StartMinute` as minutes after midnight
- `DurationMinutes`
- nullable block `Color` in `#RRGGBB` form
- audit fields and concurrency token

Require lecturer email for persisted entries. Obtain it from lecturer desiderata when selected; adapt manual entry UI to collect or select an email. Normalize email with trim and lowercase for comparisons, but preserve the display name snapshot.

Use integer minutes instead of decimal hours. Require start and duration to align to 15-minute increments, require positive duration, and keep entries within the supported daily bounds unless product requirements explicitly change them.

### ScheduleEntryGroup

Model entry-to-group assignment as a many-to-many join with composite primary key `(ScheduleEntryId, StudentGroupId)`. A block may serve one or several groups. Replace persisted `group` and `groupSpan` coordinates with group IDs; derive column position/span only in the frontend. Verify that every assigned group belongs to the entry's schedule.

Require at least one group per entry.

### ScheduleComment

Persist `Id`, `ScheduleEntryId`, `Body`, `AuthorEmail`, `AuthorDisplayName`, `AuthorRole`, `CreatedAt`, nullable `UpdatedAt`, nullable `DeletedAt`, and nullable `DeletedBy`.

Use soft deletion. Return active comments by default in chronological order. The current planner-facing frontend grants every admitted user read/write access; authors may edit/delete their comments and admins may delete any comment. Do not implement the future lecturer read-only view yet.

## Enforce scheduling rules

Reject overlapping entries that share at least one student group within the same schedule. Allow room and lecturer overlaps to be saved because the current UI treats them as warnings, not hard constraints.

Perform group-overlap validation transactionally. Serialize mutations per schedule with a PostgreSQL transaction/advisory lock or an equivalently safe mechanism so two concurrent requests cannot both pass validation and create an invalid group overlap.

Use half-open ranges: `[StartMinute, StartMinute + DurationMinutes)`. Adjacent entries do not overlap.

Do not copy comments when cloning an entry.

## Apply authorization and audit identity

Require a valid Keycloak bearer token for all API operations. Use the authenticated email claim as `CreatedBy`, `UpdatedBy`, comment author identity, and ownership check. Read the display name from token claims when available. Map realm roles as existing services do.

For the current planner tool, authorize users already admitted to the schedule frontend for both reads and writes. Keep service policies explicit so a future lecturer policy can add read/comment access without weakening planner mutations. Do not broaden the host route to lecturers yet.

Never trust author/audit fields supplied by the client.

## Use optimistic concurrency

Expose a concurrency token for schedules, groups, and entries. Require it on update/delete operations and regenerate it after a successful mutation. Return HTTP `409 Conflict` with Problem Details when a token is stale. Do not silently overwrite another planner's changes.

No full audit history or schedule-version history is required. Preserve only creation/update metadata, comment edits, and comment soft deletion.

## Shape the API around UI operations

Use `/api/v1/schedules` inside the service; local nginx exposes the service under `/api-schedule/`.

Provide at minimum:

- list/filter schedules by faculty, academic year, semester number, and study mode
- create a schedule and retrieve its complete weekly snapshot
- update schedule metadata/status with concurrency
- create, rename, reorder, and delete groups with concurrency
- save the complete edited group/entry working copy in one transaction with schedule concurrency
- list, add, edit, and soft-delete entry comments

Return a complete schedule snapshot containing ordered groups and entries for initial page load. Keep plan edits in a frontend working copy and submit groups and entries together through an explicit `save` endpoint. Validate and replace the aggregate children transactionally only when the supplied schedule concurrency token is current. Return the saved snapshot and a new token. Comments remain focused, immediately persisted resources and are not part of the plan save transaction.

Use camelCase JSON and RFC 7807 Problem Details. Validate request DTOs at the application boundary. Use `400` for malformed input, `404` for missing resources, `409` for concurrency or uniqueness conflicts, and `422` for validly shaped commands that violate scheduling rules.

## Configure PostgreSQL and local deployment

Add PostgreSQL to `deployment-local/docker-compose.databases.yml` with:

- an official pinned PostgreSQL image
- dedicated database and non-root application credentials
- named persistent volume
- health check
- host port exposed for local database tools
- membership in `shogun_local_network`

Add non-secret defaults/placeholders to `.env.local.example`. Pass the connection string to the API through environment configuration. Do not commit real credentials.

Add `schedule-api` to `deployment-local/docker-compose.yml`, wait for or tolerate database readiness, attach it to `shogun_local`, and add it to proxy dependencies. Route `/api-schedule/` to the container in `deployment-local/nginx.local.conf`. Do not edit the non-local backend compose/proxy unless explicitly requested.

Apply EF migrations automatically for local container startup with bounded retries. Do not use `EnsureCreated`. Keep migrations committed and deterministic.

## Replace frontend prototype storage

Replace `MockDataService` with an HTTP-backed schedule store while retaining signals for UI state. Load the schedule snapshot based on active faculty, academic year, semester number, and study mode. Maintain a dirty working copy for create/edit/move/copy/resize/color/room/group operations. Persist it only through an explicit `Zapisz zmiany` action. Persist comments immediately and reconcile returned comments.

Provide an academic-year plan selector plus create/delete plan actions. Academic years represent yearly editions such as `2026/2027`; they are not student cohorts. Preserve semester-number selection inside the chosen year. Confirm destructive plan deletion.

On stale save, keep the dirty working copy, show the concurrency conflict, disable/reject further save attempts against the stale token, and offer `Odśwież z serwera`. Warn that refresh discards local unsaved changes and require confirmation when dirty. Do not silently merge or overwrite concurrent edits.

Replace comment `localStorage` persistence and demo seeding with API calls. Keep the drawer UX and permissions. Surface API failures through the existing toast mechanism and roll back optimistic UI state or refresh the affected snapshot.

Translate between API minutes and frontend decimal hours only at the API boundary. Translate entry group IDs into grid columns and derive group spans only when assigned groups are adjacent; prevent or clearly handle non-adjacent multi-group assignments.

Keep lecturer availability in the Assignments API. Store only lecturer email/display snapshot and subject snapshot in Schedule; do not duplicate desiderata availability records.
